# ADR-002: Uso de Kong API Gateway para centralizar el acceso a microservicios

* **Estado:** Propuesto
* **Decisores:** Equipo de arquitectura y líderes técnicos
* **Stakeholders:** Equipos de desarrollo, seguridad, operaciones, QA y producto
* **Fecha:** 2026-11-10

---

## 1. Contexto y Declaración del Problema

Como caso práctico, se construirá una plataforma de comercio electrónico compuesta inicialmente por tres microservicios REST: **Clientes**, **Catálogo** y **Pedidos**. Una aplicación web y una aplicación móvil consumirán estos servicios desde redes externas. Exponer cada microservicio directamente obligaría a los clientes a conocer múltiples direcciones y a cada equipo a implementar por separado autenticación, límites de consumo, CORS, registro de solicitudes y otras políticas transversales.

Se necesita un punto de entrada único que enrute las solicitudes hacia el servicio correspondiente y aplique controles consistentes sin incorporar lógica de negocio. Para el caso práctico, el gateway publicará rutas como `/api/clientes`, `/api/catalogo` y `/api/pedidos`, validará tokens JWT, limitará el número de solicitudes por consumidor y generará información de observabilidad antes de reenviar cada petición al microservicio correspondiente.

La solución debe poder ejecutarse en contenedores, admitir configuración automatizada y versionada, facilitar la incorporación de nuevos servicios y evitar una dependencia excesiva de un lenguaje o framework. También se consideran el costo de infraestructura, la latencia adicional, la disponibilidad, la seguridad y la curva de aprendizaje del equipo.

---

## 2. Opciones Consideradas

* **Opción 1: Kong API Gateway.** Desplegar Kong como punto de entrada único y configurar rutas, servicios, autenticación JWT, rate limiting, CORS, logging y métricas mediante sus capacidades y plugins.
* **Opción 2: Spring Cloud Gateway.** Construir y mantener una aplicación Java con Spring Cloud Gateway para implementar el enrutamiento y los filtros transversales requeridos.
* **Opción 3: Exponer los microservicios directamente.** Permitir que las aplicaciones cliente se comuniquen con cada microservicio y que cada servicio implemente sus propias políticas transversales.

---

## 3. Decisión Tomada

Decidimos seleccionar **Kong API Gateway** porque proporciona de forma integrada el enrutamiento y las políticas transversales necesarias para el caso práctico, sin requerir el desarrollo y mantenimiento de un gateway propio. Su modelo de configuración y sus plugins permiten aplicar controles homogéneos a microservicios desarrollados con distintas tecnologías y reducen el tiempo necesario para disponer de una solución funcional.

Kong se utilizará para gestionar el tráfico **norte-sur**, es decir, las solicitudes que ingresan desde los clientes hacia la plataforma. No reemplazará la autorización específica del dominio ni la comunicación interna que deba realizarse directamente entre microservicios.

### Razones Principales de la Elección

* **Punto de entrada unificado:** los clientes solo necesitan conocer el dominio del gateway, mientras Kong enruta las solicitudes hacia Clientes, Catálogo y Pedidos.
* **Políticas transversales reutilizables:** los plugins permiten configurar JWT, rate limiting, CORS, transformación de solicitudes, logging y métricas sin repetir su implementación en cada microservicio.
* **Independencia tecnológica:** al tratarse de un componente independiente, no obliga a que los microservicios utilicen Java, Spring o un framework específico.
* **Menor esfuerzo de desarrollo:** se reutilizan capacidades probadas en lugar de construir, probar y mantener filtros propios para seguridad y control de tráfico.
* **Configuración automatizable:** las rutas y políticas pueden administrarse de forma declarativa, almacenarse en Git y desplegarse mediante procesos repetibles.
* **Escalabilidad de la solución:** la incorporación de nuevos microservicios o consumidores requiere principalmente cambios de configuración, no modificaciones en todas las aplicaciones cliente.

## 4. Análisis Comparativo de Opciones (Pros y Contras)

### Opción 1: Kong API Gateway

* **Ventajas:**
  * Centraliza el enrutamiento y ofrece una API pública estable aunque cambien las direcciones internas de los microservicios.
  * Dispone de plugins para autenticación, control de tráfico, seguridad, transformación y observabilidad.
  * Reduce la duplicación de código transversal y favorece la aplicación consistente de políticas.
  * Es independiente del lenguaje de los microservicios y puede ejecutarse en contenedores.
  * Permite versionar y automatizar su configuración, lo que facilita reproducir los entornos del caso práctico.
  * Su comunidad, documentación y ecosistema facilitan el aprendizaje y la resolución de problemas.
* **Desventajas:**
  * Agrega un componente que debe desplegarse, configurarse, monitorearse, actualizarse y asegurarse.
  * Introduce un salto de red adicional y, por tanto, cierta latencia y consumo de recursos.
  * Puede convertirse en punto único de falla si no se configuran réplicas, health checks y una estrategia de alta disponibilidad.
  * Algunas capacidades, plugins o ediciones pueden tener condiciones de licencia y costos que deben evaluarse antes de adoptarlos.
  * Una configuración excesiva o la inclusión de lógica de negocio en plugins puede aumentar el acoplamiento con el gateway.

### Opción 2: Spring Cloud Gateway

* **Ventajas:**
  * Se integra de forma natural con aplicaciones Java y con el ecosistema Spring.
  * Ofrece flexibilidad para implementar predicados y filtros personalizados mediante código.
  * Puede ser conveniente cuando el equipo domina Spring y requiere comportamientos muy específicos.
* **Desventajas:**
  * Requiere desarrollar, probar, empaquetar y mantener una aplicación adicional.
  * Las políticas personalizadas incrementan la cantidad de código propio y la carga de mantenimiento.
  * Está más vinculado al ecosistema Java, aunque pueda enrutar solicitudes hacia servicios escritos en otros lenguajes.
  * Para el alcance del caso práctico, supone mayor esfuerzo inicial que configurar las capacidades ya disponibles en Kong.

### Opción 3: Exponer los microservicios directamente

* **Ventajas:**
  * Reduce el número de componentes de infraestructura y evita el salto de red del gateway.
  * Puede ser suficiente para una prueba local muy pequeña con un único servicio y sin consumidores externos.
* **Desventajas:**
  * Obliga a los clientes a administrar múltiples endpoints y dificulta cambiar la topología interna.
  * Duplica autenticación, rate limiting, CORS y logging en cada microservicio.
  * Incrementa la superficie expuesta y puede generar políticas de seguridad inconsistentes.
  * Acopla las aplicaciones cliente a la ubicación y a los detalles de despliegue de cada servicio.

## 5. Consecuencias e Impacto

### Positivas (Beneficios)

* Las aplicaciones web y móvil consumirán un único punto de entrada, independientemente de la ubicación interna de los microservicios.
* Los equipos podrán concentrarse en las reglas de negocio y delegar al gateway las políticas transversales que le correspondan.
* La validación centralizada de JWT y los límites de consumo reducirán solicitudes inválidas o abusivas hacia los servicios internos.
* Los logs y las métricas del gateway proporcionarán una visión común del tráfico de entrada, la latencia y los errores.
* Las rutas y políticas versionadas permitirán revisar cambios, repetir despliegues y revertir configuraciones de manera controlada.
* Los microservicios podrán permanecer en una red interna sin exponer públicamente cada endpoint.

### Negativas / Riesgos (Compromisos)

* La operación incluirá un componente crítico adicional y deberá contemplar su escalado, disponibilidad y recuperación.
* La configuración incorrecta de rutas o plugins puede afectar simultáneamente a varios microservicios.
* El gateway no elimina la necesidad de aplicar autorización y validaciones de negocio dentro de cada microservicio.
* La validación centralizada del token no sustituye la protección de la red interna ni la gestión segura de claves y secretos.
* El equipo deberá aprender el modelo de configuración de Kong y controlar la compatibilidad de versiones y plugins.

Para el caso práctico, la configuración de Kong se almacenará en Git y se validará antes de cada despliegue. Se definirán health checks, límites de recursos, logs estructurados y métricas; en un entorno productivo se utilizarán al menos dos réplicas. Los secretos no se incluirán en los archivos de configuración y los cambios se probarán primero en un entorno no productivo. El gateway se limitará a funciones transversales, evitando incorporar reglas de negocio que correspondan a los microservicios.
