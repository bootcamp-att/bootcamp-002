El patrón Strangler Fig suele considerarse mejor que un Big Bang Rewrite para modernizar un sistema o repositorio porque permite reemplazarlo gradualmente, en vez de reescribir y sustituir todo de una sola vez.

Ventajas de Strangler Fig
Menor riesgo: cada módulo se migra, prueba y despliega por separado.
Entregas continuas: el sistema antiguo puede seguir funcionando mientras se construye el nuevo.
Retroalimentación temprana: los usuarios prueban partes modernizadas antes de completar toda la migración.
Reversión sencilla: si algo falla, se puede redirigir esa funcionalidad al sistema anterior.
Progreso visible en GitHub: los pull requests son más pequeños, revisables y fáciles de integrar.
Menos conflictos: varios equipos pueden migrar componentes independientes sin mantener durante años una gran rama de reescritura.
Conserva el conocimiento existente: evita intentar reproducir de golpe reglas de negocio que quizá no estén documentadas.
Riesgos del Big Bang Rewrite
Una reescritura total suele tardar mucho sin producir valor visible. Durante ese periodo, el sistema original continúa cambiando, por lo que el nuevo puede quedar desactualizado antes de publicarse. Además, el lanzamiento concentra muchos errores y decisiones arquitectónicas en un solo momento.

Pero Strangler Fig no siempre es mejor
También introduce complejidad temporal: enrutamiento entre sistemas, adaptadores, duplicación de datos y mantenimiento simultáneo de dos arquitecturas. Un Big Bang Rewrite puede ser razonable cuando el proyecto es pequeño, está bien especificado, puede detenerse durante la migración o el sistema anterior resulta imposible de integrar.

En resumen: Strangler Fig suele ser preferible para sistemas grandes y activos porque transforma una migración de alto riesgo en una serie de cambios pequeños y reversibles. GitHub facilita este enfoque mediante ramas cortas, pull requests, pruebas automatizadas, feature flags y despliegues progresivos.
